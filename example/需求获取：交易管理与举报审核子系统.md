# 需求获取：交易管理、举报审核与AI服务子系统

> 项目：校园二手商品交易系统  
> 范围：交易管理子系统、举报与审核子系统、AI服务子系统  
> 阶段：需求获取  
> 说明：本文只覆盖本人负责的三个子系统，不展开用户认证、商品发布、私信、统计等其他模块。

---

## 一、系统范围与目标

本部分负责校园二手商品交易系统中的三类核心业务：

1. **交易管理子系统**  
   支持买家对商品发起交易申请，卖家接受或拒绝，双方取消，买家确认完成，并联动商品状态和订单状态。

2. **举报与审核子系统（人工）**  
   支持用户对商品、用户、订单进行举报和申诉；支持管理员处理举报、裁决申诉、审核校园认证、审核商品，并执行处罚动作。

3. **AI服务子系统（AI辅助审核 + AI客服）**  
   提供独立的 AI 服务，辅助管理员对商品、评论、举报、认证进行智能化初筛；同时为用户提供基于 RAG 知识库的智能客服对话（支持 SSE 流式输出）。

系统目标：

- 让校园二手交易从“浏览商品”走到“线下面交完成”，形成订单闭环。
- 让违规商品、违规用户、虚假认证能够被举报、人工审核处理，形成治理闭环。
- 引入 AI 辅助能力，提升审核效率，并通过 AI 客服降低用户咨询成本。
- 订单状态、商品状态、审核状态必须一致、可追踪、可通知。AI 失败能自动降级，不阻断主业务。

## 三、自然语言需求描述

### 3.1 交易管理子系统

1. 买家应能对**审核通过且在售**的商品发起交易申请。  
   申请时填写买家留言、期望交易地点、期望交易时间。

2. 系统应校验：
   - 商品存在；
   - 商品 `audit_status = approved`；
   - 商品 `status = on_sale`；
   - 买家不是卖家本人；
   - 该商品没有待处理或已接受的订单。

3. 系统应生成唯一订单号和雪花 ID，订单状态为 `pending`，并保存下单时的商品价格快照。

4. 卖家应能查看“我卖出的”订单列表，按状态筛选，并查看订单详情。

5. 卖家应能接受交易。接受后：
   - 订单状态变为 `accepted`；
   - 商品状态变为 `reserved`；
   - 系统通知买家。

6. 卖家应能拒绝交易。拒绝后：
   - 订单状态变为 `rejected`；
   - 记录拒绝原因；
   - 商品状态不变，仍为 `on_sale`；
   - 系统通知买家。

7. 买家应能查看“我买到的”订单列表，按状态筛选，并查看订单详情。

8. 买卖双方应能在 `pending` 或 `accepted` 状态下取消订单。取消后：
   - 订单状态变为 `cancelled`；
   - 记录取消原因；
   - 商品状态恢复为 `on_sale`；
   - 系统通知对方。

9. 买家应能在 `accepted` 状态下确认交易完成。完成后：
   - 订单状态变为 `completed`；
   - 记录完成时间；
   - 商品状态变为 `sold`；
   - 系统通知双方。

10. 只有订单买卖双方能查看订单详情，其他用户不能越权查看。

11. 订单状态变化、商品状态变化应通过消息模块发送站内信通知相关用户。

### 3.2 举报与审核子系统（人工）

1. 用户应能对以下对象提交举报：
   - 商品 `product`；
   - 用户 `user`；
   - 订单 `order`。

2. 提交举报时填写：
   - 举报原因；
   - 详细描述；
   - 最多 9 张证据图片。

3. 系统应校验：
   - 举报对象存在；
   - 不能举报自己；
   - 同一用户不能重复举报同一对象；
   - 图片文件必须属于当前用户。

4. 用户应能查看“我的举报”列表和举报详情。  
   举报详情只有举报人本人可以查看。

5. 被举报人应能在举报已处理之后提交申诉。  
   一条举报只能申诉一次。

6. 管理员应能查看全平台举报列表和详情，支持按状态、举报对象类型筛选。

7. 管理员应能处理举报：
   - 判定为有效 `valid` 或无效 `invalid`；
   - 举报有效时选择处罚动作：
     - `none`：仅记录；
     - `offline`：强制下架商品；
     - `ban`：封禁用户；
     - `warn`：警告用户；
   - 记录处理说明、处理管理员、处理时间。

8. 管理员应能查看申诉列表，并处理申诉：
   - 通过 `approved`；
   - 驳回 `rejected`；
   - 记录处理说明。

9. 管理员应能查看校园认证审核列表，并审核认证：
   - 通过后更新用户 `certified = 1`；
   - 拒绝时记录拒绝原因；
   - 只能审核 `pending` 状态的认证。

10. 管理员应能对 `pending` 状态的商品进行人工审核：
    - 通过：商品保持 `on_sale`；
    - 拒绝：商品 `audit_status = rejected`，`status = offline`，记录拒绝原因。

11. 举报处理、申诉处理、认证审核、商品审核的结果，都应通过消息模块通知相关用户。

### 3.3 AI服务子系统

#### 3.3.1 AI 辅助审核

1. 系统应提供统一的 AI 审核接口，支持对以下业务进行智能初筛：
   - 商品 `product`；
   - 评论 `review`；
   - 举报 `report`；
   - 认证 `certification`。

2. AI 审核的输入应包含：
   - 审核类型 `audit_type`；
   - 文本字段 `text_fields`（键名对齐 Java 实体字段名）；
   - 图片 URL 列表 `image_urls`（支持 http/https 链接或 base64 data URL）。

3. AI 审核应返回结构化的结果，包含：
   - 是否通过 `passed`；
   - 理由 `reason`；
   - 风险分类 `risk_category`（违禁品/色情低俗/虚假信息/联系方式引流/辱骂攻击/身份存疑/正常）；
   - 风险等级 `risk_level`（low/medium/high）；
   - 建议动作 `suggested_action`（通过/驳回/人工复核）。

4. AI 服务的返回结构应兼容 Java 端的 `Result` 格式（`{code, msg, data}`）。业务异常统一返回 HTTP 200 + `code=0`，避免 OpenFeign 抛出非 2xx 异常。

5. Java 后端在关键业务节点应调用 AI 审核：
   - 商品发布后异步自动审核；
   - 管理端查看商品、评论、举报、认证详情时辅助审核。

6. AI 审核仅作为“辅助”，最终决定权在管理端人工审核。当 AI 调用失败或超时时，Java 后端应自动降级，不阻断主流程，交由人工判断。

#### 3.3.2 AI 智能客服

1. 系统应提供基于 RAG 知识库的智能客服对话接口，支持同步返回和 SSE 流式输出。

2. 客服知识库由平台帮助文档（`.md` / `.txt`）构成，系统应支持文档切分、向量化并存入向量数据库（Chroma）。

3. 对话时，系统应根据用户输入检索最相关的 top-K 知识片段，并拼入提示词中。

4. 系统应支持多会话隔离，通过 `session_id` 区分不同用户的对话历史。会话历史目前存储在服务进程内存中，需保证单实例可用。

5. 系统应支持 SSE 流式输出，逐步返回 AI 回复内容，提升用户体验。

6. 当知识库缺失、损坏或检索失败时，AI 客服应自动降级为纯对话模式，不影响基本问答功能。

7. AI 服务启动时应注册到 Nacos，Java 后端通过 OpenFeign 以服务名 `ai-service` 进行发现和调用。流式接口由 Java 端使用 HTTP 客户端直连（Feign 不支持 SSE）。

### 6.9 UC-AI06 AI客服流式对话

| 用例名称     | AI客服流式对话                                               |
| 用例标识     | UC-AI06                                                      |
| 执行者       | 用户                                                         |
| 目标         | 用户与 AI 客服进行基于 RAG 知识的问答，并实时获取流式回答    |

## 八、下一步建议

这份内容已经可以作为你大作业的**需求获取初稿**。  
下一步进入**阶段 2.0 协同修订**时，可以让虚拟同伴重点审查：

1. 订单状态机是否完整，是否缺少“超时未处理自动取消”；
2. 举报处罚是否应该自动联动信用分；
3. 申诉通过后是否应该撤销处罚；
4. AI 审核失败或超时时，降级为人工审核的策略是否足够健壮；
5. AI 客服会话历史存在内存中，多实例部署时如何迁移到 Redis；
6. 把“AI 审核要快”“安全性好”等模糊需求改写成可量化验收标准（如响应时间 < 3 秒）。
