# 软件工程课程笔记：需求分析与软件设计

> 基于 PPT 内容整理，涵盖第 4 章（需求获取、需求分析）与第 5 章（体系结构设计、接口与详细设计）。

---

## 📘 第一部分：第 4 章 需求获取
**核心逻辑：需求是从哪里来的？如何初步记录和表达？**

### 1. 需求获取渠道与方法
*   **五大渠道：**
    1.  从用户和客户导出（最直接）。
    2.  软件开发者构思和创作（创新性）。
    3.  重用已有系统的需求（复用）。
    4.  分解其他系统的需求产生新需求（衍生）。
    5.  从互联网群体贡献中获取（众包/开源）。
*   **五大方法：**
    *   **访谈：** 正式（具体问题）与非正式（开放性问题）。关注整体目标、诱导需求、会谈效率。
    *   **调查问卷：** 针对不同角色的用户，了解业务流程、实际操作和期望。
    *   **现场观摩：** 观察业务工作流程及细节。
    *   **分析业务资料：** 行业标准、规则、网络资料。
    *   **软件原型：** 快速构建可运行的产品原型。**特点**：直观可操作，能挖掘新需求，但无法描述具体细节。**过程**：获得初始需求 → 建立原型 → 评估原型/挖掘新需求 → 确认需求。

### 2. 初步需求描述
*   **三种描述方式对比：**
    *   **自然语言：** 简单明了，但容易有歧义，难以区分功能与非功能需求。
    *   **软件原型：** 直观，但仅仅是梗概，未涉及详细陈述。
    *   **用例描述（核心）：** 基于图形化符号，描述软件边界、用例及关系。不可运行，但利于多方沟通。
*   **用例模型深度解析：**
    *   **执行者（Actor）：** 系统外实体（用户、软件系统、硬件设备）。确定方法（主执行者、副执行者、需要控制的硬件、需要交互的系统等）。
    *   **用例（Use Case）：** 外部可见的、相对独立完整的业务目标。从本质上讲，是用户与计算机之间的一次典型交互作用。
    *   **关系：**
        *   `<<include>>`（包含）：提取公共行为（必须执行）。
        *   `<<Extend>>`（扩展）：添加可选动作（特殊情境下触发）。
        *   **泛化：** 继承关系（子用例是父用例的特殊形式）。
    *   **详细描述：** 必须区分**基本的动作序列**（不考虑例外）和**扩展的动作序列**（异常或特殊情境）。

### 3. 需求文档化及评审
*   **需求规格说明书内容：** 软件背景、待解决问题、解决方案（软硬件集成等）、功能性需求（用例）、非功能性需求（质量/约束）、可行性及风险。
*   **评审 8 大质量属性：** 中肯性、合理性、完整性、必要性、溯源性、准确性、正确性、一致性。

## 📗 第二部分：第 4 章 需求分析
**核心逻辑：如何把初步需求变成精确、可执行、可验证的模型？**

### 1. 需求分析任务与过程
*   **解决的问题：** 初步需求不详尽、不清晰、关系不明朗、未区分重要性。
*   **核心动作：** 精化需求（消除歧义、补全遗漏） + 建立需求模型（图形化/可视化）。
*   **审查标准：** 有效性（符合用户）、一致性（描述一致）、全面性（包含所有约束）、可检验性（有验证标准）。
*   **迭代流程：** 分析并确定优先级 → 建立需求模型（输出 DFD、类图等） → 文档化需求 → 确认和验证需求。

### 2. 需求优先级分析
*   **核心视角：** 区分**核心需求**（特色、优势、举足轻重）与**外围需求**（次要、辅助）。
*   **划分方法：**
    *   **MoSCoW 法：** Must have（核心业务，必做）、Should have（重要业务，应做）、Could have（附加业务，可做）、Won't have（高成本低价值，暂不做）。
    *   **KANO 模型：** 基本型（必须有）、期望型（越多越好）、兴奋型（意料之外）。
*   **实操流程：** 复查目标 → 识别边界（核心/外围） → MoSCoW 划分 → 评审合理性 → 结合依赖、风险、资源制定**迭代计划**。
*   **案例（居家老人监测看护系统）：**
    *   核心用例（M 级）：观察、跟随、获取信息、检测异常、通知异常。放入 V1、V2 版本（感知与告警）。
    *   外围用例（S/C 级）：交互、控制机器人、登录、设置。放入 V3、V4 版本。

### 3. 需求模型
*   **建模思想：** 自顶向下、逐步求精。
*   **两大流派对比：**
    1.  **结构化建模（面向数据流）：** 认为功能表现为对数据的处理。
        *   **DFD（数据流图）：** 描述数据走向、处理过程、存储（结合数据字典）。
        *   **ER 图（实体-联系图）：** 描述实体、属性及关联。
        *   **STD（状态转换图）：** 描述状态变化及触发条件。
    2.  **面向对象建模（UML）：** 认为世界由对象构成。
        *   **用例图：** 系统功能及边界。
        *   **类图：** 类、属性、操作、继承、关联等。
        *   **活动图：** 业务流程、分支与并行。
        *   **状态图：** 单个对象的生命周期。
        *   **顺序图：** 按时间顺序描述对象间的消息交互。
*   **建模原则：** 抽象到具体、兼顾可读与实用、边界清晰、保持一致。

### 4. 需求验证
*   **重要性：** 发现错误越早，成本越低（需求阶段 1 倍，发布后 200 倍以上）。
*   **可验证性三要素：**
    *   **可测：** 有明确的验证方法。
    *   **可量化：** 质量需求有指标、阈值（例：95% 请求响应 ≤ 2 秒）。
    *   **可追踪：** 需求来源和去向可查（使用 RTM 矩阵）。
*   **不可验证需求的修订：** 识别主观词/模糊词 → 澄清真实意图 → 定义场景（Given-When-Then） → 确定指标阈值 → 约定验证方法。
*   **保障方法：** 需求评审、原型验证、测试用例驱动、建模验证、仿真分析。

## 📙 第三部分：第 5 章 体系结构设计
**核心逻辑：如何为系统搭建全局性的骨架和技术解决方案？**

### 1. 软件体系结构基础
*   **定义：** 系统的基础组织，包含构件、构件间关系、环境关系及设计原则。
*   **三要素：**
    *   **构件：** 基本功能部件（可分离、可替换、可复用）。
    *   **连接件：** 构件间的交互关系（过程调用、消息传递、事件通知等）。
    *   **约束：** 必须满足的条件（如分层系统中高层可调用低层，反之不可）。

### 2. 体系结构设计过程
*   **输入：** 功能需求、质量需求、开发约束需求。
*   **流程：** 设计初步结构 → 重用资源（如框架） → 精化结构 → 设计部署模型 → 文档化与评审（迭代过程）。

### 3. 典型体系结构风格
*   **管道和过滤器：** 适合数据流特征，可独立升级过滤器，但不适合交互应用。
*   **层次体系结构：** 分层依赖，松耦合，支持增量开发（如 OSI 七层模型）。
*   **客户机/服务器（C/S）：** 共享不对等资源，数据与应用分布处理。
*   **MVC 结构：** 模型（业务逻辑）+ 视图（显示）+ 控制器（交互）。可扩展、可维护，适合 Web/UI 开发。
*   **事件驱动架构（EDA）：** 以事件为核心，包括事件源、事件通道、事件响应。解耦、易扩展、可异步削峰，但数据一致性复杂、调试困难。
*   **电话销售系统案例分析：**
    *   **最终结论：** 主体采用**分层架构**（表示层/业务层/数据访问层），Web 层采用 **MVC**，特定场景（定时拨号、无效号码提示）采用**事件驱动架构（EDA）**。

## 📕 第四部分：第 5 章 接口、数据与详细设计
**核心逻辑：如何把高层架构细化为可直接编码的局部设计？**

### 1. 接口设计
*   **分类：** 用户接口（UI）、外部接口（系统间/硬件）、内部接口（模块间方法调用/消息）。
*   **用户界面设计原则：** 用户熟悉、一致性、意外最小化、可恢复性（撤销/确认）、用户指南、用户差异性。
*   **内部接口设计 6 原则：**
    1.  最小化（只暴露必要方法，5-8 个）。
    2.  意图明确（命名清晰，如 `createOrder`）。
    3.  无副作用（查询不修改状态）。
    4.  参数精简（不超过 5 个，超过则封装为对象）。
    5.  返回值明确（不用 0/1 或 null，用 Result 对象或 Optional）。
    6.  异常处理分层（明确抛出 `ValidationException` 等）。
*   **API 设计 5 原则：** 契约优先、向后兼容、无状态优先、错误信息明确、响应格式统一。

### 2. 数据设计
*   **工作内容：** 确定持久化数据 → 确定存储方式 → 设计操作 → 评审。
*   **原则：** 无冗余、权衡时空效率、验证完整性。

### 3. 详细设计
*   **定位：** 体系结构设计与编码之间的桥梁，关注**实现细节**（抽象层次低、粒度小）。
*   **核心任务：**
    1.  细化模块（高内聚低耦合）。
    2.  细化接口（参数、调用方式）。
    3.  设计内部数据结构与算法。
    4.  设计处理逻辑（流程图）。
    5.  设计异常处理机制。
*   **原则：** 针对需求、深入优化、足够详细（能指导编码）、充分重用。

| :------ | :------- | :------------- | :----------- | :----------- |

### 3. 可量化的需求描述句式
*   **通用句式：** 在【什么条件】下，【什么指标】达到【什么阈值】，通过【什么验证方法】验证。
    *   *示例：* 在 1000 并发用户时，95% 的查询请求响应时间 ≤ 2 秒，99% ≤ 5 秒；验证方式：使用性能测试工具进行性能测试。
*   **冲突权衡句式：** 【什么指标】在【什么条件】下冲突，按【什么原则】权衡，用【什么验证方法】验证。
    *   *示例：* 性能与成本在“响应 ≤ 1 秒且不增加服务器成本”约束下冲突，按照优先保证核心体验、控制成本的原则进行权衡。

### 4. 内部接口设计的代码规范
*   **不推荐（参数过多/返回值不明）：**

```java
void createOrder(Long userId, String productId, int quantity, String couponCode, String shippingAddress, Date deliveryDate, String paymentMethod);
int process(Order order); // int 返回值含义不明
```

*   **推荐（封装参数对象/明确返回值）：**

```java
void createOrder(CreateOrderRequest request); // 参数封装为对象
OrderResult getOrderStatus(Long orderId); // 返回明确的 Result 对象
Optional<User> findById(Long id); // 明确表示可能不存在，避免空指针
```
