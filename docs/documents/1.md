## 一、模块概述

用户认证模块是系统的基础模块，负责确认用户身份并签发访问凭证。所有其他模块都依赖本模块提供的用户身份信息。

### 1.1 模块职责

| 职责       | 说明                                  |
| ---------- | ------------------------------------- |
| 用户注册   | 通过手机号验证码创建新账号            |
| 用户登录   | 校验账号密码，签发 JWT token          |
| 用户登出   | 使当前 token 立即失效                 |
| 发送验证码 | 向指定手机号发送验证码                |
| 重置密码   | 通过手机号验证码重置密码              |
| 身份校验   | 拦截请求，解析 token，注入当前用户 ID |

### 1.2 模块边界

**做：**

- 确认"你是谁"
- 签发和校验 token
- 管理验证码

**不做：**

- 权限判断（由拦截器和管理端模块负责）
- 用户资料管理（属于个人中心模块）
- 校园认证（属于个人中心模块）

## 二、功能设计

### 2.1 功能清单

| 编号 | 功能         | 接口                           | 是否需登录 |
| ---- | ------------ | ------------------------------ | ---------- |
| F1   | 发送验证码   | POST /user/auth/send-code      | 否         |
| F2   | 用户注册     | POST /user/auth/register       | 否         |
| F3   | 用户登录     | POST /user/auth/login          | 否         |
| F4   | 用户登出     | POST /user/auth/logout         | 是         |
| F5   | 重置密码     | POST /user/auth/reset-password | 否         |
| F6   | 获取当前用户 | GET /user/auth/me              | 是         |

### 2.2 发送验证码

**流程：**

1. 前端传入手机号
2. 校验手机号格式（^1[3-9]\d{9}$）
3. 生成 6 位随机数字
4. 存入 Redis：campus:sms:code:{phone} = 验证码，TTL 5 分钟
5. 调用短信服务发送（MVP 阶段打印日志）
6. 返回成功

**入参：**

| 参数  | 类型   | 必填 | 说明   |
| ----- | ------ | ---- | ------ |
| phone | String | 是   | 手机号 |

**返回：** Result<Void>

### 2.3 用户注册

**流程：**

1. 前端传入：用户名、密码、手机号、验证码
2. 参数格式校验
3. 从 Redis 取验证码比对
4. 检查用户名是否已存在
5. 检查手机号是否已注册
6. 密码 BCrypt 加密
7. 构造 User 对象，写入数据库
8. 删除 Redis 验证码
9. 返回新用户 ID

**入参：**

| 参数     | 类型   | 必填 | 约束             |
| -------- | ------ | ---- | ---------------- |
| username | String | 是   | 4-20 字符，唯一  |
| password | String | 是   | 6-32 字符        |
| phone    | String | 是   | 手机号格式，唯一 |
| code     | String | 是   | 6 位验证码       |

**返回：** Result<Long>（新用户 ID）

### 2.4 用户登录

**流程：**

1. 前端传入：用户名、密码
2. 查用户，不存在则报错
3. BCrypt 校验密码，不匹配则报错
4. 检查账号状态，被封禁则报错
5. 生成 JWT token（有效期 7 天）
6. 返回 token 和用户基本信息

**入参：**

| 参数     | 类型   | 必填 |
| -------- | ------ | ---- |
| username | String | 是   |
| password | String | 是   |

**返回：** Result<LoginVO>

| 字段     | 类型   | 说明      |
| -------- | ------ | --------- |
| token    | String | JWT token |
| userId   | Long   | 用户 ID   |
| username | String | 用户名    |
| nickname | String | 昵称      |
| avatar   | String | 头像      |
| role     | String | 角色      |

### 2.5 用户登出

**流程：**

1. 从请求头取 token
2. 去掉 Bearer 前缀
3. 解析 token 拿过期时间
4. 计算剩余有效期
5. 把 token 写入 Redis 黑名单，TTL = 剩余有效期
6. 返回成功

**返回：** Result<Void>

**说明：** 登出后，原 token 在剩余有效期内被拦截器拒绝。

### 2.6 重置密码

**流程：**

1. 前端传入：手机号、验证码、新密码
2. 校验验证码
3. 查手机号是否已注册
4. 新密码 BCrypt 加密
5. 更新 user 表
6. 删除验证码
7. 返回成功

**入参：**

| 参数        | 类型   | 必填 |
| ----------- | ------ | ---- |
| phone       | String | 是   |
| code        | String | 是   |
| newPassword | String | 是   |

**返回：** Result<Void>

### 2.7 获取当前用户

**流程：**

1. 拦截器解析 token，把 userId 放入 ThreadLocal
2. Controller 从 BaseContext 取出 userId
3. 查 user 表返回用户信息

**返回：** Result<UserVO>

## 三、数据库设计

### 3.1 user 表

```sql
CREATE TABLE IF NOT EXISTS `user` (
    `id`           BIGINT       NOT NULL COMMENT '用户ID',
    `username`     VARCHAR(50)  NOT NULL COMMENT '用户名',
    `password`     VARCHAR(100) NOT NULL COMMENT '密码(BCrypt)',
    `nickname`     VARCHAR(50)  DEFAULT NULL COMMENT '昵称',
    `avatar`       VARCHAR(255) DEFAULT NULL COMMENT '头像URL',
    `phone`        VARCHAR(20)  DEFAULT NULL COMMENT '手机号',
    `email`        VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
    `role`         VARCHAR(20)  NOT NULL DEFAULT 'USER' COMMENT '角色',
    `status`       VARCHAR(20)  NOT NULL DEFAULT 'normal' COMMENT '状态',
    `certified`    TINYINT      NOT NULL DEFAULT 0 COMMENT '是否校园认证',
    `credit_score` INT          NOT NULL DEFAULT 100 COMMENT '信用分',
    `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    `deleted`      TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_username` (`username`),
    UNIQUE KEY `uk_phone` (`phone`),
    KEY `idx_status` (`status`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
```

### 3.2 字段说明

| 字段         | 说明                 | 约束            |
| ------------ | -------------------- | --------------- |
| id           | 主键，应用生成       | 唯一            |
| username     | 登录账号             | 唯一，4-20 字符 |
| password     | BCrypt 哈希，60 字符 | 非空            |
| phone        | 手机号               | 唯一，11 位     |
| role         | USER / ADMIN         | 默认 USER       |
| status       | normal / banned      | 默认 normal     |
| certified    | 0 未认证 / 1 已认证  | 默认 0          |
| credit_score | 信用分               | 默认 100        |
| deleted      | 逻辑删除             | 默认 0          |

## 四、Redis 设计

### 4.1 Key 列表

| Key                            | 类型   | TTL              | 用途       |
| ------------------------------ | ------ | ---------------- | ---------- |
| campus:sms:code:{phone}        | String | 5 分钟           | 短信验证码 |
| campus:token:blacklist:{token} | String | token 剩余有效期 | 登出黑名单 |

### 4.2 验证码

```
key:   campus:sms:code:13800138000
value: 6 位数字
TTL:   5 分钟
```

- 发送时写入
- 注册或重置密码时读取
- 校验通过后删除
- 到期自动清理

### 4.3 Token 黑名单

```
key:   campus:token:blacklist:eyJhbGciOiJIUzI1NiJ9...
value: "1"
TTL:   token 剩余有效期
```

- 登出时写入
- 修改密码时写入
- 拦截器每次请求前检查
- 到期自动清理

## 五、安全设计

### 5.1 密码存储

- 使用 BCrypt 哈希，cost = 10
- 数据库不存明文
- 每个密码自动加盐，相同密码哈希不同

### 5.2 JWT 设计

**Payload 结构：**

```json
{
  "userId": 1001,
  "type": "user",
  "role": "USER",
  "iat": 1726905600,
  "exp": 1727510400
}
```

| 字段   | 说明               |
| ------ | ------------------ |
| userId | 用户 ID            |
| type   | 区分用户端和管理端 |
| role   | 角色               |
| iat    | 签发时间           |
| exp    | 过期时间（7 天）   |

**签名算法：** HS256

**密钥：** 配置在 application-dev.yml，生产环境用环境变量覆盖

### 5.3 拦截器

**拦截路径：** /user/**

**放行路径：**

```
/user/auth/register
/user/auth/login
/user/auth/send-code
/user/auth/reset-password
```

**校验流程：**

1. 从请求头取 Authorization
2. 去掉 Bearer 前缀
3. 查 Redis 黑名单
   - 命中 → 401
   - 未命中 → 继续
4. 解析 JWT
5. 校验 type = user
6. 把 userId 放入 BaseContext
7. 放行

### 5.4 登出黑名单

**为什么需要：**

JWT 是无状态的，服务端不存储 token，所以无法主动失效。

**方案：**

登出时把 token 写入 Redis 黑名单，TTL 为 token 剩余有效期。拦截器每次请求前检查黑名单。

**为什么 TTL 是剩余有效期：**

token 过期后自然失效，黑名单只需覆盖"还未过期但已登出"的窗口期，过期后自动清理，避免 Redis 无限增长。

**黑名单 vs 白名单：**

| 对比项     | 黑名单              | 白名单         |
| ---------- | ------------------- | -------------- |
| 存什么     | 已登出的 token      | 所有有效 token |
| 数据量     | 小                  | 大             |
| Redis 挂了 | 正常 token 不受影响 | 全部用户被踢   |
| 踢人下线   | 不能                | 能             |

校园平台用户量小，黑名单足够。

## 十、设计决策记录

| 决策         | 选择               | 原因                           |
| ------------ | ------------------ | ------------------------------ |
| 密码算法     | BCrypt             | 自带盐、可调难度、抗暴力破解   |
| 认证方式     | JWT                | 无状态、易扩展、适合前后端分离 |
| 验证码存储   | Redis              | 短生命周期、支持 TTL           |
| 登出方案     | Redis 黑名单       | 解决 JWT 无法主动失效的问题    |
| token 有效期 | 7 天               | 平衡安全性和用户体验           |
| 拦截器实现   | HandlerInterceptor | 与 Spring MVC 集成，简单直接   |
