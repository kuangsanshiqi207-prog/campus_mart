> 模块：管理端-举报管理
> 版本：V1.0
> 更新日期：2026-09-24

## 一、模块概述

举报管理模块是管理端的内容治理核心模块，负责用户提交举报的处理和申诉的裁决。管理员根据举报内容判定成立与否，并执行处罚动作（警告/下架/封禁），被举报人可提交申诉。

### 1.1 模块职责

| 职责     | 说明                               |
| -------- | ---------------------------------- |
| 举报列表 | 查询全平台举报，支持状态和类型筛选 |
| 举报详情 | 查看举报完整信息，含证据图片       |
| 处理举报 | 判定有效/无效，执行处罚动作        |
| 申诉列表 | 查询全平台申诉                     |
| 处理申诉 | 裁决申诉通过/驳回                  |

### 1.2 模块边界

**做：**

- 举报的查询和处理
- 申诉的查询和裁决
- 处罚动作执行（下架商品、封禁用户、警告）

**不做：**

- 举报的提交（属于用户端举报模块）
- 申诉的提交（属于用户端举报模块）
- 自动处罚（AI 审核模块负责）

### 1.3 治理闭环

```
用户 A 举报商品 X
    ↓
管理员处理 → 举报成立（valid）
    ↓
执行处罚（下架/封禁/警告）
    ↓
被举报人（卖家）收到通知，可以申诉
    ↓
管理员处理申诉 → 通过（撤销处罚）/ 驳回（维持处罚）
```

### 1.4 与用户端举报模块的关系

| 数据     | 用户端举报模块   | 管理端举报管理    |
| -------- | ---------------- | ----------------- |
| 数据范围 | 只看自己提交的   | 看全平台          |
| 操作     | 提交、查看       | 处理、裁决        |
| 路径     | /user/reports/** | /admin/reports/** |
| 权限     | 登录用户         | 管理员            |

## 二、功能设计

### 2.1 功能清单

| 编号 | 功能     | 接口                           | 是否需登录 |
| ---- | -------- | ------------------------------ | ---------- |
| F1   | 举报列表 | GET /admin/reports             | 是         |
| F2   | 举报详情 | GET /admin/reports/{id}        | 是         |
| F3   | 处理举报 | PUT /admin/reports/{id}/handle | 是         |
| F4   | 申诉列表 | GET /admin/appeals             | 是         |
| F5   | 处理申诉 | PUT /admin/appeals/{id}/handle | 是         |

### 2.2 举报列表

**流程：**

1. 接收查询条件（status、targetType、分页）
2. 组装 SQL 条件
3. 分页查询 report 表（deleted = 0）
4. 关联查举报人昵称
5. 转 ReportVO
6. 返回 PageResult

**入参：**

| 参数       | 类型    | 必填 | 说明                  |
| ---------- | ------- | ---- | --------------------- |
| status     | String  | 否   | pending/valid/invalid |
| targetType | String  | 否   | product/user/order    |
| pageNum    | Integer | 否   | 默认 1                |
| pageSize   | Integer | 否   | 默认 10               |

**返回：** Result<PageResult<ReportVO>>

### 2.3 举报详情

**流程：**

1. 查举报，不存在报错
2. 关联查举报人昵称
3. 转 ReportVO
4. 返回

**返回：** Result<ReportVO>

### 2.4 处理举报

**流程：**

1. 从 BaseContext 取 adminId
2. 查举报，不存在报错
3. 校验状态是 pending
4. 校验结果合法（valid/invalid）
5. 更新 report：
   - status = valid/invalid
   - action：举报成立时按入参；举报不成立时设为 none
   - handle_reason
   - handler_id = adminId
   - handle_time = NOW()
6. 举报成立时执行处罚动作：
   - offline：下架商品，通知卖家
   - ban：封禁用户，通知被封禁人
   - warn：警告用户，通知被警告人
   - none：仅记录，不处罚
7. 通知举报人处理结果
8. 返回

**入参：**

| 参数   | 类型   | 必填 | 说明                  |
| ------ | ------ | ---- | --------------------- |
| result | String | 是   | valid/invalid         |
| action | String | 否   | none/offline/ban/warn |
| reason | String | 否   | 处理说明              |

**返回：** Result<Void>

**处罚动作说明：**

| action  | 说明           |
| ------- | -------------- |
| none    | 不处罚，仅记录 |
| offline | 强制下架商品   |
| ban     | 封禁用户       |
| warn    | 警告用户       |

### 2.5 申诉列表

**流程：**

1. 接收查询条件（status、分页）
2. 分页查询 appeal 表（deleted = 0）
3. 关联查申诉人昵称
4. 转 AppealVO
5. 返回 PageResult

**入参：**

| 参数     | 类型    | 必填 | 说明                      |
| -------- | ------- | ---- | ------------------------- |
| status   | String  | 否   | pending/approved/rejected |
| pageNum  | Integer | 否   | 默认 1                    |
| pageSize | Integer | 否   | 默认 10                   |

**返回：** Result<PageResult<AppealVO>>

### 2.6 处理申诉

**流程：**

1. 从 BaseContext 取 adminId
2. 查申诉，不存在报错
3. 校验状态是 pending
4. 校验结果合法（approve/reject）
5. 更新 appeal：
   - approve → status = approved
   - reject → status = rejected
   - handle_reason
   - handler_id = adminId
   - handle_time = NOW()
6. 通知申诉人处理结果
7. 返回

**入参：**

| 参数   | 类型   | 必填 | 说明           |
| ------ | ------ | ---- | -------------- |
| result | String | 是   | approve/reject |
| reason | String | 否   | 处理说明       |

**返回：** Result<Void>

**说明：** MVP 阶段申诉通过不撤销处罚，仅记录状态。后期优化时可联动恢复商品/解封用户。

## 三、数据库设计

**复用举报模块已建的表，不新增表。**

### 3.1 report 表

```sql
CREATE TABLE IF NOT EXISTS `report` (
    `id`            BIGINT       NOT NULL COMMENT '主键',
    `reporter_id`   BIGINT       NOT NULL COMMENT '举报人ID',
    `target_type`   VARCHAR(20)  NOT NULL COMMENT '举报对象类型 product/user/order',
    `target_id`     BIGINT       NOT NULL COMMENT '举报对象ID',
    `reason`        VARCHAR(100) NOT NULL COMMENT '举报原因（短）',
    `description`   VARCHAR(500) DEFAULT NULL COMMENT '详细描述',
    `images`        VARCHAR(2000) DEFAULT NULL COMMENT '证据图片URL列表，逗号分隔',
    `status`        VARCHAR(20)  NOT NULL DEFAULT 'pending' COMMENT 'pending/valid/invalid',
    `action`        VARCHAR(20)  DEFAULT NULL COMMENT '处理动作 none/offline/ban/warn',
    `handle_reason` VARCHAR(255) DEFAULT NULL COMMENT '处理说明',
    `handler_id`    BIGINT       DEFAULT NULL COMMENT '处理管理员ID',
    `handle_time`   DATETIME     DEFAULT NULL COMMENT '处理时间',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `deleted`       TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    KEY `idx_reporter_id` (`reporter_id`),
    KEY `idx_target` (`target_type`, `target_id`),
    KEY `idx_status` (`status`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '举报表';
```

### 3.2 appeal 表

```sql
CREATE TABLE IF NOT EXISTS `appeal` (
    `id`            BIGINT       NOT NULL COMMENT '主键',
    `report_id`     BIGINT       NOT NULL COMMENT '举报ID',
    `user_id`       BIGINT       NOT NULL COMMENT '申诉人ID（被举报人）',
    `reason`        VARCHAR(500) NOT NULL COMMENT '申诉理由',
    `images`        VARCHAR(2000) DEFAULT NULL COMMENT '证据图片URL列表',
    `status`        VARCHAR(20)  NOT NULL DEFAULT 'pending' COMMENT 'pending/approved/rejected',
    `handle_reason` VARCHAR(255) DEFAULT NULL COMMENT '处理说明',
    `handler_id`    BIGINT       DEFAULT NULL COMMENT '处理管理员ID',
    `handle_time`   DATETIME     DEFAULT NULL COMMENT '处理时间',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `deleted`       TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_report` (`report_id`),
    KEY `idx_user_id` (`user_id`),
    KEY `idx_status` (`status`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '申诉表';
```

### 3.3 表关系

```
user   1---N report (作为举报人)
user   1---N appeal (作为申诉人)
report 1---1 appeal
admin  1---N report (作为处理人)
admin  1---N appeal (作为处理人)
```

## 五、安全设计

### 5.1 权限隔离

管理端接口在 `/admin/reports/**` 和 `/admin/appeals/**` 下：

- 用户 token 不能访问（type 校验）
- 只有管理员 token 能访问

### 5.2 操作权限

MVP 阶段，所有管理员都能操作举报管理功能。

**后续优化：** 按角色细分，可限制为审核员角色。

### 5.3 关键操作留痕

| 操作     | 留痕                                        |
| -------- | ------------------------------------------- |
| 处理举报 | 记录 handler_id、handle_time、handle_reason |
| 处理申诉 | 记录 handler_id、handle_time、handle_reason |
| 处罚动作 | 通过 MessageSender 通知被处罚人             |

### 5.4 防止误操作

| 保护         | 说明                       |
| ------------ | -------------------------- |
| 状态校验     | 只能处理 pending 举报/申诉 |
| 结果枚举校验 | 只接受合法枚举值           |
| 事务保证     | 举报更新 + 处罚动作同事务  |

## 十、设计决策记录

| 决策         | 选择                         | 原因                     |
| ------------ | ---------------------------- | ------------------------ |
| 复用已有表   | report + appeal              | 数据结构一致             |
| Mapper 复用  | 用户端 Mapper 追加方法       | 减少重复代码             |
| 处理动作     | 独立于举报状态               | 举报成立后可选择处罚方式 |
| 举报不成立   | action 强制为 none           | 避免误伤                 |
| 处罚动作执行 | 在 Service 层调用其他 Mapper | 简单直接，MVP 不做异步   |
| 申诉通过     | MVP 不撤销处罚，只记录状态   | 简化流程                 |
| 事务         | 举报更新 + 处罚动作同事务    | 保证一致性               |
| 通知机制     | 复用 MessageSender           | 解耦，统一消息入口       |
| 权限         | MVP 不细分角色               | 后期按角色控制           |
