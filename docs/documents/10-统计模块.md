## 一、模块概述

个人统计模块负责展示用户自己的各类数据统计，包括商品、交易、评价、信用分和趋势。与管理端的全平台统计不同，个人统计只展示当前用户自己的数据。

### 1.1 模块职责

| 职责       | 说明                                             |
| ---------- | ------------------------------------------------ |
| 数据概览   | 商品、订单、评价、信用分、收藏、未读数的综合概览 |
| 商品统计   | 各状态商品数量、浏览量、收藏量                   |
| 交易统计   | 买入卖出数量、金额、待处理                       |
| 评价统计   | 收到评价数、各星级分布、好评率                   |
| 信用分流水 | 信用分变动记录                                   |
| 信用分趋势 | 按天的信用分变化                                 |
| 交易趋势   | 按天的订单数量变化                               |

### 1.2 模块边界

**做：**

- 只读统计，不修改任何业务数据
- 数据来源：product、order、review、favorite、message、credit_log
- 跨模块聚合

**不做：**

- 数据的写入（属于各业务模块）
- 全平台统计（属于管理端统计）
- 导出（MVP 阶段不做）

### 1.3 与市集模块的关系

市集模块的 `UserProductStatsVO` 和 `ProductMapper.getMyStats` 已在"我的商店"模块中实现。

**个人统计模块直接复用**，不重复开发。

### 1.4 与管理端统计的区别

| 对比         | 个人统计           | 管理端统计      |
| ------------ | ------------------ | --------------- |
| 数据范围     | 只看自己           | 看全平台        |
| 目的         | 了解自己的交易情况 | 运营监控        |
| 权限         | 登录用户           | 管理员          |
| 路径         | /user/stats/**     | /admin/stats/** |
| 是否含信用分 | 是                 | 否              |
| 是否含导出   | 否                 | 是              |

| orderSellTotal | Integer | 我卖出的订单数 |

| creditScore    | Integer | 当前信用分     |
| reviewCount    | Integer | 收到的评价数   |
| avgScore       | Double  | 平均评分       |
| favoriteCount  | Integer | 收藏商品数     |
| unreadMessage  | Long    | 未读消息数     |

**流程：**

3. 空值兜底
4. 返回

**返回：** Result<UserOrderStatsVO>

| 字段          | 类型       | 说明       |
| ------------- | ---------- | ---------- |
| buyTotal      | Integer    | 买到的总数 |
| sellTotal     | Integer    | 卖出的总数 |
| buyCompleted  | Integer    | 买入已完成 |
| sellCompleted | Integer    | 卖出已完成 |
| buyAmount     | BigDecimal | 买入总金额 |
| sellAmount    | BigDecimal | 卖出总金额 |

### 2.5 我的评价统计

**流程：**

1. 从 BaseContext 取 userId
2. 聚合查询 review 表：
   - 收到评价数
   - 平均分
   - 各星级数量
   - 好评率（4-5星占比）
3. 空值兜底
4. 返回

**返回：** Result<UserReviewStatsVO>

| 字段          | 类型    | 说明       |
| ------------- | ------- | ---------- |
| receivedTotal | Integer | 收到评价数 |
| sentTotal     | Integer | 发出评价数 |
| avgScore      | Double  | 平均分     |
| score5Count   | Integer | 5 星数     |
| score4Count   | Integer | 4 星数     |
| score3Count   | Integer | 3 星数     |
| score2Count   | Integer | 2 星数     |
| score1Count   | Integer | 1 星数     |
| goodRate      | Double  | 好评率     |

### 2.6 信用分流水

**流程：**

1. 从 BaseContext 取 userId
2. 按 userId 查 credit_log 表
3. 按创建时间倒序
4. 分页返回

**入参：**

| 参数     | 类型    | 必填 | 说明    |
| -------- | ------- | ---- | ------- |
| pageNum  | Integer | 否   | 默认 1  |
| pageSize | Integer | 否   | 默认 10 |

**返回：** Result<PageResult>

### 2.7 信用分趋势

**流程：**

1. 从 BaseContext 取 userId
2. 计算起始日期 `今天 - days + 1`
3. 按天查询 credit_log，每天取平均分
4. 补齐没有数据的日期（值为 0）
5. 返回日期列表和数值列表

**入参：**

| 参数 | 类型    | 必填 | 说明                |
| ---- | ------- | ---- | ------------------- |
| days | Integer | 否   | 默认 30，范围 1-365 |

**返回：** Result<TrendVO>

### 2.8 交易趋势

**流程：**

1. 从 BaseContext 取 userId
2. 根据 type（buy/sell）判断视角
3. 计算起始日期
4. 按天查询 order 表数量
5. 补齐没有数据的日期
6. 返回

**入参：**

| 参数 | 类型    | 必填 | 说明                |
| ---- | ------- | ---- | ------------------- |
| type | String  | 否   | buy/sell，默认 buy  |
| days | Integer | 否   | 默认 30，范围 1-365 |

**返回：** Result<TrendVO>

### 2.9 趋势数据补齐

**问题：** SQL 只能查到有数据的日期。

**示例：** 用户 7 天没交易，8 天前和 9 天前各有一单，30 天查询时只能查到 2 个日期。

**解决方案：** Service 层补齐。

```
1. 生成完整的日期列表（startDate 到 today）
2. 把 SQL 结果放进 Map<日期, 数值>
3. 遍历日期列表，从 Map 取值，没有则填 0
4. 返回等长的 dates 和 values
```

**好处：** 前端直接画图，不用处理缺失日期。

## 三、数据库设计

### 3.1 credit_log 表（新增）

```sql
CREATE TABLE IF NOT EXISTS `credit_log` (
    `id`            BIGINT       NOT NULL COMMENT '主键',
    `user_id`       BIGINT       NOT NULL COMMENT '用户ID',
    `delta`         INT          NOT NULL COMMENT '变动值（正加负减）',
    `before_score`  INT          NOT NULL COMMENT '变动前信用分',
    `after_score`   INT          NOT NULL COMMENT '变动后信用分',
    `reason`        VARCHAR(255) NOT NULL COMMENT '变动原因',
    `biz_type`      VARCHAR(20)  DEFAULT NULL COMMENT '业务类型 order/report/review',
    `biz_id`        BIGINT       DEFAULT NULL COMMENT '业务ID',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_user_time` (`user_id`, `create_time`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '信用分流水表';
```

### 3.2 字段说明

| 字段         | 说明               | 约束                |
| ------------ | ------------------ | ------------------- |
| id           | 主键，雪花算法生成 | 唯一                |
| user_id      | 用户ID             | 关联 user.id        |
| delta        | 变动值             | 正数加分，负数扣分  |
| before_score | 变动前分数         | -                   |
| after_score  | 变动后分数         | -                   |
| reason       | 变动原因           | 非空                |
| biz_type     | 业务类型           | order/report/review |
| biz_id       | 业务ID             | 关联业务记录        |
| create_time  | 变动时间           | -                   |

### 3.3 索引

**`idx_user_time`（user_id, create_time）：**

- 查询某个用户的流水：`WHERE user_id = ? ORDER BY create_time DESC`
- 查询某个用户的趋势：`WHERE user_id = ? AND create_time >= ?`

**复合索引先按 user_id 过滤，再按时间排序，避免回表。**

### 3.4 与 user 表的关系

```text
user.credit_score     当前信用分（冗余）
credit_log            变动记录（明细）
```

**两个数据必须同步更新：**

```java
// 修改信用分时
user.creditScore += delta;
creditLog.insert(...);  // 记录变动
```

**MVP 阶段：** 暂时没有自动扣分的业务，`credit_log` 只在管理端手动调整时写入。

### 3.5 数据来源汇总

| 统计项     | 来源表     |
| ---------- | ---------- |
| 商品总数   | product    |
| 在售商品   | product    |
| 已售出商品 | product    |
| 我买到的   | order      |
| 我卖出的   | order      |
| 待处理订单 | order      |
| 收到的评价 | review     |
| 平均评分   | review     |
| 收藏数     | favorite   |
| 未读消息   | message    |
| 信用分     | user       |
| 信用分流水 | credit_log |

**个人统计模块不新增业务表**，只新增 credit_log。

## 四、SQL 设计要点

### 4.1 一次查询聚合多个指标

**不用多次查询，用 `SUM(CASE WHEN ...)` 一次搞定：**

```sql
SELECT
    COALESCE(SUM(CASE WHEN buyer_id = ? THEN 1 ELSE 0 END), 0) AS buyTotal,
    COALESCE(SUM(CASE WHEN seller_id = ? THEN 1 ELSE 0 END), 0) AS sellTotal,
    COALESCE(SUM(CASE WHEN buyer_id = ? AND status = 'completed' THEN 1 ELSE 0 END), 0) AS buyCompleted,
    ...
FROM `order`
WHERE deleted = 0 AND (buyer_id = ? OR seller_id = ?)
```

**好处：** 一次 SQL 完成所有统计，减少数据库往返。

### 4.2 COALESCE 兜底

```sql
COALESCE(SUM(...), 0) AS xxx
```

**作用：** 没有数据时返回 0 而不是 NULL。

**原因：** `SUM` 在没有匹配行时返回 NULL，前端拿到 NULL 会出错。

### 4.3 平均分也要兜底

```sql
COALESCE(AVG(score), 0) AS avgScore
```

没有评价时返回 0，而不是 NULL。

### 4.4 好评率计算

```sql
COALESCE(SUM(CASE WHEN score >= 4 THEN 1 ELSE 0 END) / COUNT(*) * 100, 0) AS goodRate
```

**注意：** 如果 `COUNT(*) = 0`，会除零错误。**MySQL 里除零返回 NULL**，被 `COALESCE` 兜底为 0。

### 4.5 趋势查询

```sql
SELECT DATE(create_time) AS date, COUNT(*) AS value
FROM `order`
WHERE user_id = ? AND create_time >= ?
GROUP BY DATE(create_time)
ORDER BY date ASC
```

**按天分组，返回 Map 列表。**

## 五、安全设计

### 5.1 数据隔离

**所有查询都从 BaseContext 取 userId，不接受前端传入。**

```java
Long userId = BaseContext.getCurrentId();
```

**不加会怎样：** A 用户能查 B 用户的统计。

### 5.2 全部接口需登录

`/user/stats/**` 拦截器不放行，未登录 401。

### 5.3 参数范围限制

| 参数     | 限制     |
| -------- | -------- |
| pageNum  | ≥ 1      |
| pageSize | 1-100    |
| days     | 1-365    |
| type     | buy/sell |

**Service 层做默认值和范围检查**，避免 SQL 注入和越界。

## 六、异常处理

### 6.1 业务异常

本模块**不抛业务异常**，所有空值用 COALESCE 兜底。

### 6.2 参数校验

分页和 days 在 Service 层做默认值和范围检查。

### 6.3 未登录

拦截器返回 401。

## 十、设计决策记录

| 决策       | 选择                  | 原因                 |
| ---------- | --------------------- | -------------------- |
| 统计方式   | 实时查询              | 数据量小，实时性好   |
| 聚合查询   | 单 SQL 多指标         | 减少数据库往返       |
| 空值兜底   | COALESCE              | 避免 NULL 传递到前端 |
| 商品统计   | 复用市集模块          | 不重复开发           |
| 趋势补齐   | Service 层补齐        | 前端直接画图         |
| 信用分流水 | 独立表                | 记录变动历史         |
| 数据隔离   | BaseContext 取 userId | 防止越权             |
| 参数范围   | Service 层校验        | 防止 SQL 注入        |
| 全部需登录 | 拦截器                | 个人数据             |
| 缓存       | 不用                  | 个人统计访问频率低   |
