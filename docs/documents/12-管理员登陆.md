# 管理端认证模块设计文档

> 模块：管理端认证
> 版本：V1.0
> 更新日期：2026-09-24

---

## 一、模块概述

管理端认证模块负责管理员的登录、登出和身份校验，是管理端的入口。管理员通过独立于用户端的账号体系登录，签发独立的管理员 JWT token。

### 1.1 模块职责

| 职责           | 说明                             |
| -------------- | -------------------------------- |
| 管理员登录     | 校验用户名密码，签发管理员 token |
| 管理员登出     | 当前 token 加入黑名单            |
| 身份校验       | 拦截器校验 token 并注入管理员 ID |
| 当前管理员信息 | 查询当前登录管理员               |

### 1.2 模块边界

**做：**

- 管理员登录、登出、身份校验
- 管理员独立 token 管理

**不做：**

- 用户端注册登录（属于用户端认证模块）
- 管理员权限细分（MVP 只区分 SUPER_ADMIN / ADMIN）
- 管理员操作日志（后续系统模块补充）

### 1.3 与用户端认证的区别

| 对比         | 用户端认证              | 管理端认证               |
| ------------ | ----------------------- | ------------------------ |
| 账号表       | user                    | admin                    |
| 路径前缀     | /user/**                | /admin/**                |
| 拦截器       | JwtTokenUserInterceptor | JwtTokenAdminInterceptor |
| JWT 密钥     | userSecretKey           | adminSecretKey           |
| token 有效期 | 7 天                    | 2 小时                   |
| claim type   | user                    | admin                    |
| 用户角色     | USER                    | ADMIN / SUPER_ADMIN      |
| 注册         | 开放注册                | 管理员创建               |

## 二、功能设计

### 2.1 功能清单

| 编号 | 功能           | 接口                    | 是否需登录 |
| ---- | -------------- | ----------------------- | ---------- |
| F1   | 管理员登录     | POST /admin/auth/login  | 否         |
| F2   | 管理员登出     | POST /admin/auth/logout | 是         |
| F3   | 当前管理员信息 | GET /admin/auth/profile | 是         |

### 2.2 管理员登录

**流程：**

1. 接收用户名、密码
2. 查 admin 表
   - 不存在 → 报错"用户名或密码错误"
3. BCrypt 校验密码
   - 不匹配 → 报错"用户名或密码错误"
4. 校验账号状态
   - banned → 报错"账号已被封禁"
5. 签发管理员 JWT token：
   - claims 携带 userId、type=admin
   - 用 adminSecretKey 签名
   - 有效期 adminTtl（2 小时）
6. 返回 token 和管理员基本信息

**入参：**

| 参数     | 类型   | 必填 | 约束 |
| -------- | ------ | ---- | ---- |
| username | String | 是   | 非空 |
| password | String | 是   | 非空 |

**返回：** Result<LoginVO>

| 字段     | 类型   | 说明                   |
| -------- | ------ | ---------------------- |
| token    | String | 管理员 JWT             |
| userId   | Long   | 管理员 ID              |
| username | String | 用户名                 |
| nickname | String | 昵称                   |
| avatar   | String | 头像                   |
| role     | String | 角色 SUPER_ADMIN/ADMIN |

### 2.3 管理员登出

**流程：**

1. 从请求头取 token
2. 去掉 Bearer 前缀
3. 解析 token 拿过期时间
4. 计算剩余有效期
5. 写入 Redis 黑名单，TTL = 剩余有效期
6. 返回成功

**说明：** 与用户端登出机制一致，用同一套 Redis 黑名单 key。

### 2.4 当前管理员信息

**流程：**

1. 拦截器已把 userId 放入 BaseContext
2. 从 BaseContext 取 userId
3. 查 admin 表
4. 返回 AdminVO

**返回：** Result<AdminVO>

## 三、数据库设计

### 3.1 admin 表

```sql
CREATE TABLE IF NOT EXISTS `admin` (
    `id`          BIGINT       NOT NULL COMMENT '主键',
    `username`    VARCHAR(50)  NOT NULL COMMENT '用户名',
    `password`    VARCHAR(100) NOT NULL COMMENT '密码(BCrypt)',
    `nickname`    VARCHAR(50)  DEFAULT NULL COMMENT '昵称',
    `avatar`      VARCHAR(255) DEFAULT NULL COMMENT '头像',
    `role`        VARCHAR(20)  NOT NULL DEFAULT 'ADMIN' COMMENT 'SUPER_ADMIN/ADMIN',
    `status`      VARCHAR(20)  NOT NULL DEFAULT 'normal' COMMENT 'normal/banned',
    `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    `deleted`     TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_username` (`username`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '管理员表';
```

### 3.2 字段说明

| 字段     | 说明               | 约束              |
| -------- | ------------------ | ----------------- |
| id       | 主键，雪花算法生成 | 唯一              |
| username | 登录账号           | 唯一              |
| password | BCrypt 哈希        | 非空              |
| nickname | 昵称               | 可空              |
| avatar   | 头像               | 可空              |
| role     | 角色               | SUPER_ADMIN/ADMIN |
| status   | 状态               | normal/banned     |

### 3.3 角色说明

| 角色        | 权限                             |
| ----------- | -------------------------------- |
| SUPER_ADMIN | 全部权限，包括管理员管理         |
| ADMIN       | 日常管理权限，不能操作管理员账号 |

### 3.4 初始化超级管理员

```sql
-- 密码明文 123456，使用 BCrypt 加密
INSERT INTO `admin` (id, username, password, nickname, role, status)
VALUES (1, 'admin', '${BCrypt哈希}', '超级管理员', 'SUPER_ADMIN', 'normal')
ON DUPLICATE KEY UPDATE `username` = `username`;
```

**生成 BCrypt 哈希：**

```java
System.out.println(new BCryptPasswordEncoder().encode("123456"));
```

### 3.5 与 user 表的关系

```text
user   用户端账号，买卖双方
admin  管理端账号，平台管理员
两个表完全独立，互不关联
```

**为什么独立：**

- 管理员不参与交易，不需要信用分、认证等字段
- 用户不参与平台管理
- 职责分离，避免权限混淆

## 四、JWT 设计

### 4.1 Payload 结构

```json
{
  "userId": 1,
  "type": "admin",
  "iat": 1726905600,
  "exp": 1726912800
}
```

| 字段   | 说明                      |
| ------ | ------------------------- |
| userId | 管理员 ID                 |
| type   | admin（区分用户端 token） |
| iat    | 签发时间                  |
| exp    | 过期时间（2 小时）        |

**与用户 token 的区别：**

| 项       | 用户 token    | 管理员 token   |
| -------- | ------------- | -------------- |
| 密钥     | userSecretKey | adminSecretKey |
| type     | user          | admin          |
| 过期时间 | 7 天          | 2 小时         |

**为什么管理员 token 更短：**

- 管理员权限高，泄露危害大
- 管理员操作频繁，重新登录成本低
- 遵循最小权限和最短有效期原则

### 4.2 签名算法

HS256（HMAC SHA-256）

### 4.3 Token 请求头

统一用 `Authorization`，格式：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

## 五、拦截器设计

### 5.1 拦截路径

```java
registry.addInterceptor(jwtTokenAdminInterceptor)
        .addPathPatterns("/admin/**")
        .excludePathPatterns("/admin/auth/login");
```

### 5.2 校验流程

```text
1. 放行 OPTIONS 预检请求
2. 非 HandlerMethod 直接放行
3. 从请求头取 Authorization
4. 去掉 Bearer 前缀
5. token 为空 → 401
6. 查 Redis 黑名单
   ├─ 命中 → 401
   └─ 未命中 → 继续
7. 解析 JWT（用 adminSecretKey）
8. 校验 type = admin
   ├─ 不是 → 403
   └─ 是 → 继续
9. 取 claims 里的 userId
10. 写入 BaseContext
11. 放行
```

### 5.3 与用户端拦截器的区别

| 对比         | JwtTokenUserInterceptor | JwtTokenAdminInterceptor |
| ------------ | ----------------------- | ------------------------ |
| 密钥         | userSecretKey           | adminSecretKey           |
| token 请求头 | userTokenName           | adminTokenName           |
| type 校验    | user                    | admin                    |
| 状态码       | 401                     | 401 / 403                |

### 5.4 常见坑

**坑 1：用旧 claim key**

苍穹外卖的拦截器里用的是 `EMP_ID`（"empId"），我们的 token 里是 `USER_ID`（"userId"）。

如果拦截器不改，`claims.get("empId")` 返回 null，`.toString()` 抛 NPE，被 catch 捕获后返回 401。

**修正：**

```java
Long userId = Long.valueOf(claims.get(JwtClaimsConstant.USER_ID).toString());
```

**坑 2：没去 Bearer 前缀**

token 从请求头拿到时是 `Bearer eyJ...`，直接解析会失败。

**修正：**

```java
if (token.startsWith("Bearer ")) {
    token = token.substring(7);
}
```

## 六、安全设计

### 6.1 密码存储

- BCrypt 哈希，cost = 10
- 数据库不存明文
- 自动加盐

### 6.2 Token 安全

- 独立密钥
- 短有效期
- 携带 type 标识
- 支持黑名单登出

### 6.3 登录安全

- 错误信息模糊化（统一"用户名或密码错误"）
- 账号状态校验
- 登录后返回 token，后续请求带 token

**MVP 阶段不做：**

- 登录失败次数限制
- 验证码
- 登录日志
- 异地登录提醒

### 6.4 权限隔离

管理端接口和用户端接口**完全隔离**：

- 路径不同：/admin/** vs /user/**
- 密钥不同：adminSecretKey vs userSecretKey
- 拦截器不同
- 用户 token 不能访问管理端接口（type 校验会拦截）

## 十一、设计决策记录

| 决策         | 选择                   | 原因                         |
| ------------ | ---------------------- | ---------------------------- |
| 账号体系     | 独立 admin 表          | 与用户端完全隔离             |
| 密码算法     | BCrypt                 | 自带盐、可调难度             |
| token 密钥   | adminSecretKey         | 与用户端不同，防伪造         |
| token 有效期 | 2 小时                 | 管理员权限高，短有效期更安全 |
| type 标识    | claims 里带 type=admin | 拦截器可区分两端             |
| 请求头       | Authorization          | 统一标准                     |
| 登出方案     | Redis 黑名单           | 与用户端共用                 |
| 角色         | SUPER_ADMIN/ADMIN      | MVP 简化，后期可扩展         |
| 登录失败信息 | "用户名或密码错误"     | 防止用户名枚举               |
